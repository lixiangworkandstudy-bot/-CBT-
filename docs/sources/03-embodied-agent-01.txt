一、双控制路径辨析：直接服务 vs RCP 任务图
Vbot 身上同时存在两套“让机器狗动起来”的方式：一套是传统 ROS 2 思维的直接服务 / 话题，另一套是 RCP 的任务图（DAG）。它们不是新旧替代关系，而是分工不同——用错场景，轻则动作别扭，重则触发保护性停机。

🚨 黄金法则（最易踩坑点）同一时刻、同一物理资源，绝对不要混用两条控制路径！当 RCP 任务正在占用 LEGS 腿部资源执行一段挥手动作时，严禁并发调用 /vel_cmd 发布速度，否则会导致底层电机轨迹冲突并引发保护性停机。
为什么两条路径不能无序并发？
两条路径各自维护着自己的“轨迹账本”：/vel_cmd 是每帧覆盖的连续速度流，RCP 是整段动作的时序编排。RCP 执行挥爪时，腿部目标轨迹由动作图逐帧推进；此时插进来的速度指令会直接改写电机目标，底层无法同时满足两套轨迹，只能触发保护性停机。
更隐蔽的是“任务已受理”并不等于“动作已完成”：执行预设动作拿到的 handle 只代表任务进入执行队列，此时若切回 /vel_cmd，依然是在抢 LEGS。因此两条路径应当当作两种模式来切换，而不是两个可以随意并行的按钮。
先停连续流停止向 /vel_cmd 发布速度指令，确认底盘已经静止，再进入下一步。
再交任务图通过 /rcp/execute_task 下发 RCP 任务（或调用官方预设动作），由 RCP 为任务加锁、占用其声明的资源。
等终态再放手阻塞等待任务的最终终态，确认动作结束后再切回速度控制；绝不在动作中途抢锁，也不要把“受理成功”当成“动作完成”。
💡 一句话记忆连续量走话题，离散动作走 DAG；同一资源同一时刻，只允许一条路径说话。
二、RCP 架构：用 DAG 描述一条动作流
RCP 全称 Robot Command Pipeline，它采用类似微服务工作流的 DAG（Directed Acyclic Graph，有向无环图）结构定义任务：每个节点是一个原子动作或一个模态输出，每条边代表“谁必须等谁”。因为图里不允许出现环，任务不会陷入互相等待的死锁，天然适合“表情 + 耳灯 + 身体动作”这类多模态并行编排。
下面这张图就是源文档里的“热情迎宾”动作流：两个 DAEMON 节点并行点亮表情与耳灯，汇聚到 NORMAL 的坐姿挥爪，最后由 BARRIER 统一收尾。
DAEMON节点 1屏显表情：眨眼大笑 (say_hi)
DAEMON节点 2耳灯：渐变粉色呼吸
→并行汇入
NORMAL节点 3身体动作：坐姿挥爪 (WAVE)
→完成放行
BARRIER节点 4结束屏障：恢复常态表情与待命灯
图 2 · RCP 动作流「热情迎宾」：节点 1、2 并行，节点 3 阻塞等待完成，节点 4 收尾复位
怎么读这张 DAG
节点 = 一次原子动作或模态输出：屏显表情、耳灯、身体动作各自独立，互不阻塞时才可能并行。
边 = 时序依赖：节点 1、2 指向节点 3，说明表情与耳灯先亮起来，身体动作随后开始。
策略挂在节点上：同一张图里，DAEMON 并行、NORMAL 阻塞、BARRIER 收尾，三种节奏共存。
无环 = 不死锁：依赖关系只能单向推进，不会出现 A 等 B、B 又等 A 的互锁。
📌 接口速查RCP 任务通过 Action /rcp/execute_task 下发，Action 目标为 ExecuteTaskGoal；官方预设动作以 DagPresetRef 的形式引用。本课涉及的接口标识：/vel_cmd、/rcp/execute_task、rcp_dag、aorta_action。
三、物理资源锁：Required Resources
每一个 RCP 任务必须预先声明其锁定的硬件资源枚举，防止资源死锁——这就是 Required Resources。它相当于任务的“占座凭证”：声明了哪几类硬件，任务执行期间就由它独占，别的任务或控制路径只能等锁释放。
LEGS四肢运控
HEAD头部俯仰 / 偏航电机
SCREEN面部 LCD 交互屏
LIGHT左右耳部 RGB 调制氛围灯
AUDIO_OUT板载高保真扬声器
锁的语义：谁声明，谁独占
资源锁不是“建议”，而是 RCP 内部的仲裁依据。一个任务只要声明了 LEGS，在它执行期间，任何同样需要腿部关节的指令都应让路——无论这条指令来自另一张 RCP 任务图，还是来自直接服务的 /vel_cmd。
🚨 最容易被争抢的两类资源LEGS 与 HEAD。前者是 /vel_cmd 与挥手、站起等动作的共同目标，两者相遇就是轨迹冲突；后者在转头看人、点头致意、比心等任务之间频繁交接。声明清单写得越清楚，排查“任务为什么被中断或拒绝”就越快。
也正因如此，路径切换才必须“先停流、再交图、等终态”——让旧持有者先释放锁，新任务才能安全接管硬件。
四、三大生命周期策略：NORMAL / DAEMON / BARRIER
节点何时放行后继、何时收尾，由节点上的生命周期策略（Lifecycle）决定。RCP 只有三种策略，但组合起来就能表达“并行点亮表情 + 阻塞等身体动作 + 统一复位”的完整节奏。

五、实战：调用官方预设动作（DagPresetRef）
官方系统内置了数十种高难度特技与姿态预设（如坐下、趴下、挥手、转圈）。不需要自己拆 DAG，用预设引用 DagPresetRef 就能直接调用。下面用 Aorta Python SDK 跑一遍挥手预设，并等待任务终态。
python复制
import time
from aorta import Node
from aorta.rcp import RcpClient
def play_wave():
# 建立 RCP 客户端
node = Node("vbot_wave_demo")
client = RcpClient(node)
print("🐾 正在下发官方挥手预设动作...")
# 引用预设动作 WAVE.json
handle = client.execute_preset(
preset_name="actions/WAVE.json",
timeout=10.0
)
# 等待任务结果（受理 != 执行完成，需等待最终终态）
result = handle.wait_completed()
if result.is_success:
print("🎉 挥手动作圆满完成！")
else:
print(f"❌ 动作被中断或拒绝: {result.error_message}")
if __name__ == '__main__':
play_wave()
代码要点：从受理到终态
RcpClient(node) 建立 RCP 客户端，后续的任务下发都挂在它身上。
execute_preset(preset_name="actions/WAVE.json", timeout=10.0) 引用官方预设 WAVE.json，timeout 控制本次调用的等待上限。
handle.wait_completed() 阻塞等待最终终态——受理不等于执行完成，这一步不能省。
result.is_success 为假时读取 result.error_message；动作被中断或拒绝，往往就是资源锁被抢占。
🚨 不要提前抢锁预设动作一旦下发，任务会在执行期间持有 WAVE.json 声明的资源锁。此时任何争抢同一资源的 /vel_cmd 速度流都会造成轨迹冲突，因此必须等 wait_completed() 返回、确认终态后，再恢复直接服务控制。
六、状态机规范：站起与安全趴下
比“挥手”更常被低估的是姿态切换。站起与趴下都占用 LEGS，而且各有严格的调用规范：一个走服务切模式，一个必须走安全时序。
趴下姿态必须按四肢缓降时序安全收缩lowlevel_action(SAFE_LAYDOWN_SEQUENCE=4)
站起 →服务切换手动模式
← 安全趴下四肢缓降时序
站立姿态切换手动模式后由开发者接管set_run_mode(MANUAL=0)
图 5 · 站立 / 趴下状态机：站起用 set_run_mode(MANUAL=0)，趴下必须用 SAFE_LAYDOWN_SEQUENCE=4
为什么“全零关节”会摔？
把四条腿的关节目标全部置零，看起来是“让腿归位”，实际是瞬间撤销支撑力：机器狗在重力下自由落体，关节与减速箱直接承受落地冲击。安全趴下动作 SAFE_LAYDOWN_SEQUENCE=4 的价值，就在于按四肢缓降时序收缩，让重心平滑转移、腿部落点有序。
🚨 趴下红线（原文照录）安全趴下：必须调用 lowlevel_action(SAFE_LAYDOWN_SEQUENCE=4)，按四肢缓降时序收缩；切忌凭字面意义暴力下发全零关节指令，否则机器狗会因瞬间失重重摔着地！
⚠️ 站起 / 趴下同样持锁姿态切换期间 LEGS 被占用，不要在这个窗口里发 /vel_cmd，也不要叠加另一个需要腿部的 RCP 任务；等动作结束、锁释放后再继续。
